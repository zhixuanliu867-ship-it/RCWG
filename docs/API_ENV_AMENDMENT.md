# RCWG-ENV-API-001 · 环境变更登记草案

状态：用户已经确认采用 API 与云工作流；具体提供商、模型矩阵及测量变更等待冻结。本文是实施补充，不擅自更改 RCWG 1.0 / TaskInput 1.0 / WorkIR 1.0 的版本名称。

## 持续保留的研究对象

自然语言需求条件下，联合评估算法选择、任务分解、信息传递和资源安排。正式任务族、模板、生成协议、种子编号、比较与统计设计继续参照原设计；现有代码保留原始 campaign 数目。种子编号在 API 未支持 seed 时是尝试编号，不具有可复现随机源的含义。

## 分层实施

| 层 | 新部署路线 | 测量范围 |
|---|---|---|
| 生成器 G | 固定提供商与模型 API | 请求/响应 hash、输入条件、配置、模型返回版本、时间戳、客户端延迟、usage、尝试状态 |
| 固定语义服务 E0/E1 | 如任务需要，使用单独冻结的 API 服务与统一参数 | 与 G 分账；语义请求/响应、调用/批处理与数据传递证据 |
| 外层控制面 | Google Workflows YAML | 提交、等待、失败、批次与产物位置；工作流计费步骤单列 |
| WorkIR 执行器 | 同一受控 Linux worker，后续单独验收 | 算子/控制区域、CPU、内存、I/O、数据保真与内部调度 |
| 持久化/独立验收 | 私有对象存储与独立验证流程 | 数据、计划、证据、事件、结果与 hash 对齐 |

BOOT Cloud Run Job 仅运行固定夹具。正式硬件/隔离计量通过后，统一执行器可以放入经过校准的 Linux CPU VM；外层仍使用同一云平台。Cloud Run 的资源诊断本身不会让正式 cgroup、进程树计量自动成立。

## API 特有的冻结要求

1. 为六个 G 槽位逐项选择实际可调用的模型，记录 provider、account region、endpoint API version、requested model、reported model revision、能力和采样参数。原自托管模型名称保留为历史配置，模型 API 名单另建新版本。
2. 固定工具卡、消息模板、逻辑/物理阶段输入、输出上限、思考预算、结构化输出支持与解析策略。API不支持的参数明确标记，不声称服务实现了相同随机采样。
3. 每个物理请求独立登记，尤其是 P1 的逻辑与物理两个阶段。API请求数由实际协议统计；23,040是计划生成尝试数。429、超时、拒答、格式错误、重试与父子关系均进入账本。
4. 保存请求/响应原始证据时使用私有存储；供给生成器的输入只来自公开任务包。隐藏 gold 与未来冻结测试数据不随 BOOT 包上云。数据/API许可与保留政策需要单独审核。
5. 服务版本漂移不能靠未提供的权重 hash 消除。记录可获得的版本字段、配对块时间窗和请求顺序；版本变化或接口条件变化时分批登记，必要时暂停冻结。
6. G 与 E 的服务返回结果与本地算子资源分离。重放相同计划、重放已归档语义结果和重新请求语义服务具有不同实验含义，实施时分别命名和计量。

## 指标口径

远端模型 CPU/GPU 时间与显存不可直接观察时填 `null`，携带 `NOT_OBSERVABLE`。客户端API延迟包括网络和服务排队。工作流云计费步骤与美元成本放在经济性附账。算法时间、CPU工作量、worker内存、artifact载荷/搬运和信息保真依照可观测执行侧的口径报告。

BOOT中的RSS是进程生命周期高水位，计时只覆盖固定夹具计算，不作为正式算子峰值/效率证据。正式模型间差异只能解释为选定 API 服务和配置下的差异；容量、训练、架构或基础设施的因果分解需要额外设计。
